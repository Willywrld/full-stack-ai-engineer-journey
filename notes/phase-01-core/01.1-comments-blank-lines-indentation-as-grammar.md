# Part 1: Indentation as Grammar (Bit 1)

## 1. What is Python doing with your file?

When you write Python code, you are writing **source code** — plain text in a file, usually ending in `.py`.

Example:

```python
x = 1
print(x)
```

That text is not magic. Python cannot "just run" it immediately. It has to read and understand it first. The note describes four stages:

1. **Source code** — the text you wrote.
2. **Lexer / tokenizer** — a part of Python that splits the text into small meaningful pieces called **tokens**.
3. **Parser** — a part that checks whether those tokens are arranged according to Python's grammar.
4. **Execution** — only after parsing does Python actually run the program.

A simple analogy: imagine a recipe written in English.

- The **source code** is the recipe text.
- The **lexer** chops the text into words and punctuation.
- The **parser** checks whether the sentence grammar makes sense.
- **Execution** is actually cooking the dish.

If the grammar is broken, Python stops before cooking.

---

## 2. What is a token?

A **token** is the smallest meaningful unit of source code.

Examples of tokens:

- a **name/identifier** like `x` or `total`
- a **number** like `42`
- a **string** like `"hello"`
- an **operator** like `+` or `=`
- a **keyword** like `if`, `for`, `def`, `return`
- a **newline** marker

Some terms inside that list:

- **Keyword** — a reserved word Python already uses for its own grammar. You cannot use `if` as your own variable name.
- **Identifier** — a name you create, like `x`, `total`, or `user_name`.
- **Literal** — a fixed value written directly in code, like `42`, `"hello"`, or `True`.

So when Python sees:

```python
x = 1
```

it does not see "one blob." It sees tokens roughly like:

- name `x`
- operator `=`
- number `1`
- newline

---

## 3. Lexical grammar vs syntactic grammar

The note introduces two grammar ideas:

- **Lexical grammar** — rules for forming tokens from characters.
  Example: what counts as a valid name? What counts as a number? What starts a comment?
- **Syntactic grammar** — rules for arranging tokens into valid statements and expressions.
  Example: `x = 1` is a valid arrangement. `x y` is not, because two names sit next to each other with no operator.

A **statement** is an instruction, like:

```python
x = 1
print(x)
```

An **expression** is code that produces a value, like:

```python
2 + 3
```

A **block** or **suite** is a group of statements that belong together. In Python, that grouping is shown by **indentation** — leading spaces at the start of a line.

---

## 4. The key distinction: what is ignored, and what is not?

This is the heart of the note:

- **Comments** are ignored by the interpreter. They are not executed.
- **Blank lines** are usually ignored by the parser in scripts.
- **Whitespace** is sometimes ignored and sometimes meaningful.

**Whitespace** means spaces, tabs, and similar invisible characters.

This is why the title says "as grammar." Comments and blank lines are mostly ignored, but whitespace — especially **indentation** and **newlines** — is part of Python's syntax.

If you get whitespace wrong, Python can raise:

- `IndentationError` — indentation is missing or inconsistent where Python expects a block.
- `SyntaxError` — the token arrangement is not valid Python.
- `TabError` — tabs and spaces are mixed inconsistently.

An error here means Python refuses to run the code because it cannot understand the structure.

---

## 5. Why does Python work this way?

Python uses **indentation** instead of braces like `{ }`.

In some languages, a block might look like:

```text
if (3 > 2) {
    print("yes")
}
```

Python instead writes:

```python
if 3 > 2:
    print("yes")
```

The indentation is not decoration. It tells Python: *"this `print` belongs inside the `if` block."*

The tradeoff: Python forces the visual structure of the code to match the logical structure. That makes code readable. But it also means invisible characters matter, so beginners must learn to "see" whitespace.

---

## 6. Why this matters in real code

This is not academic. In real jobs you will:

- debug syntax errors caused by indentation,
- read comments that explain why code exists,
- use blank lines to group code so humans can review it.

So the practical rule for now is:

> Python ignores some text, but not all text. Comments and blank lines are mostly for humans. Indentation and newlines are part of the grammar.

# Part 2: Comments (Bit 2)

Now we focus on comments.

A comment is text in your source code that the Python interpreter ignores. It is there for humans — you, your teammates, your future self.

In Python, a comment starts with the `#` character and continues to the end of that physical line.

A **physical line** means an actual line in the file — the line you see when you open the file in an editor.

---

## 1. The simplest comment

```python
# This whole line is a comment.
```

Line-by-line:
- `# This whole line is a comment.`
  - The `#` starts a comment. Everything after it on that line is ignored by Python.

Python does not try to execute that text. It does not check whether the English is correct. It simply skips it.

---

## 2. A comment after real code

```python
x = 1  # This part after # is a comment.
```

Line-by-line:
- `x = 1` — Python reads this as real code: assign the value `1` to the name `x`.
- `# This part after # is a comment.` — The `#` starts a comment. The rest of the line is ignored.

So Python executes only:

```python
x = 1
```

The comment is for the human reader.

A useful way to think about it:
> A comment is like a note written in the margin of a textbook. The teacher does not read the margin note aloud during the lesson, but it helps the reader understand the page.

---

## 3. A comment is not a string

This is a very common beginner confusion.

Look at this:

```python
s = "# not a comment"
```

Line-by-line:
- `s =` — we are assigning something to the name `s`.
- `"# not a comment"` — this is a **string literal**.

A **string literal** is text written inside quotes, like `"hello"` or `'hello'`. The quotes tell Python: “this is data, not grammar.”

So even though there is a `#` character inside the quotes, Python does not treat it as the start of a comment. The `#` is just an ordinary character inside the string.

The value of `s` is the characters:

```text
# not a comment
```

**Important rule:**
Inside a string literal, whitespace and `#` are data, not grammar. They are part of the value.

Compare:

```python
x = 1  # comment
```
Here `#` starts a comment because it is outside quotes.

But:

```python
s = "# comment"
```
Here `#` is inside quotes, so it is just a character in the string.

---

## 4. Why do we use comments?

Comments are used for:
- explaining **why** code exists,
- leaving **TODOs** — notes about work still to do,
- temporarily disabling code during debugging,
- documenting special cases.

A **TODO** is just a note like “remember to fix this later.” Python ignores it; it is for humans.

### The “why, not what” rule
This is a professional habit worth learning early.

**Bad comment:**
```python
x = x + 1  # increment x
```
Why is it bad? Because the code already says “increment x.” The comment repeats what is obvious. It adds noise.

**Better comment:**
```python
x = x + 1  # compensate for zero-based page index
```
This explains *why* we are adding 1. That is useful.

So the rule is:
> Prefer comments that explain **why**, not comments that repeat **what** the code already says.

---

## 5. Two special comments near the top of files

You may see these near the top of Python files:

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
```

Do not panic. They look strange, but they are still comments to Python.

### The shebang
```python
#!/usr/bin/env python3
```
- This is called a **shebang**.
- On Unix-like systems — such as Linux or macOS — the operating system may use this first line to find the Python interpreter.
- Python itself treats it as a comment.

A shebang is a special first line that tells the operating system which program should run the file. It is not part of Python’s grammar in the usual sense. It is an operating-system convention.

### The encoding cookie
```python
# -*- coding: utf-8 -*-
```
- This is an **encoding cookie**.
- An **encoding** is a rule for how text characters are stored as bytes. UTF-8 is the modern standard encoding for text.
- Python may read this in the first two lines to know the source file’s encoding.
- Modern Python defaults to UTF-8, so you rarely need it.

So: Python may pay attention to it in a special way, but it is written as a comment. For beginner code, you usually do not need to write it.

---

## 6. A docstring is not a comment

This is the most important distinction in this section.

A **docstring** is a string literal placed as the first statement inside a module, function, class, or method. It can become documentation.

A **module** is a Python file. A **function** is a reusable block of code with a name. A **class** is a blueprint for creating objects — you will learn classes later, but for now just recognize the word.

Example:

```python
def add(a, b):
    """Return the sum of a and b."""
    return a + b
```

Line-by-line:
- `def add(a, b):` — Define a function named `add` with parameters `a` and `b`. The colon `:` starts the function body.
- `"""Return the sum of a and b."""` — This is a string literal used as a docstring. It is the first statement inside the function.
- `return a + b` — Return the sum.

Now the key point:
A **docstring is not ignored** the way a comment is. Python stores it as **function metadata**.

**Metadata** means data about the code. Python can remember the docstring and make it available later. For example, you can ask Python to show the documentation of a function.

So a comment is thrown away by the interpreter. A docstring is kept as documentation attached to the function.

### Common beginner mistake
Do not use a triple-quoted string in the middle of code as if it were a comment:

```python
x = 1
"""This is not a comment."""
y = 2
```
This is still a string expression. Python does not treat it as `#`. It is not the same as a comment.

For ordinary notes inside code, use `#`. Use docstrings for documentation at the start of a function, class, or module.

---

## 7. Comment vs docstring — the clean comparison

| Feature | Comment | Docstring |
| :--- | :--- | :--- |
| **Starts with** | `#` | Triple quotes, usually `"""..."""` |
| **Ignored by interpreter?** | Yes, completely ignored | No, stored as metadata |
| **Purpose** | Notes for humans | Documentation for the code object |
| **Where** | Anywhere | First statement inside module/function/class/method |
| **Example** | `# explain why` | `"""Return the sum."""` |

A simple memory hook:
> `#` is a note in the margin.
> A docstring is a label attached to the code.

---

You should be able to look at code and answer:
- Is this `#` starting a comment, or is it inside a string?
- Is this triple-quoted text a docstring, or just a string expression?
- Is this comment explaining *why*, or just repeating *what*?
