# Comments, Blank Lines, and Indentation as Grammar

## 1. What is Python doing with your file?

When you write Python code, you are writing **source code** — plain text in a file, usually ending in `.py`.

Example:

```python
x = 1
print(x)
```

That text is not magic. Python cannot "just run" it immediately. It has to read and understand it first. The note describes four stages:

1. **Source code** — the text you wrote.
2. **Lexer / tokenizer** — a part of Python that splits the text into small meaningful pieces called **tokens**.
3. **Parser** — a part that checks whether those tokens are arranged according to Python's grammar.
4. **Execution** — only after parsing does Python actually run the program.

A simple analogy: imagine a recipe written in English.

- The **source code** is the recipe text.
- The **lexer** chops the text into words and punctuation.
- The **parser** checks whether the sentence grammar makes sense.
- **Execution** is actually cooking the dish.

If the grammar is broken, Python stops before cooking.

---

## 2. What is a token?

A **token** is the smallest meaningful unit of source code.

Examples of tokens:

- a **name/identifier** like `x` or `total`
- a **number** like `42`
- a **string** like `"hello"`
- an **operator** like `+` or `=`
- a **keyword** like `if`, `for`, `def`, `return`
- a **newline** marker

Some terms inside that list:

- **Keyword** — a reserved word Python already uses for its own grammar. You cannot use `if` as your own variable name.
- **Identifier** — a name you create, like `x`, `total`, or `user_name`.
- **Literal** — a fixed value written directly in code, like `42`, `"hello"`, or `True`.

So when Python sees:

```python
x = 1
```

it does not see "one blob." It sees tokens roughly like:

- name `x`
- operator `=`
- number `1`
- newline

---

## 3. Lexical grammar vs syntactic grammar

The note introduces two grammar ideas:

- **Lexical grammar** — rules for forming tokens from characters.
  Example: what counts as a valid name? What counts as a number? What starts a comment?
- **Syntactic grammar** — rules for arranging tokens into valid statements and expressions.
  Example: `x = 1` is a valid arrangement. `x y` is not, because two names sit next to each other with no operator.

A **statement** is an instruction, like:

```python
x = 1
print(x)
```

An **expression** is code that produces a value, like:

```python
2 + 3
```

A **block** or **suite** is a group of statements that belong together. In Python, that grouping is shown by **indentation** — leading spaces at the start of a line.

---

## 4. The key distinction: what is ignored, and what is not?

This is the heart of the note:

- **Comments** are ignored by the interpreter. They are not executed.
- **Blank lines** are usually ignored by the parser in scripts.
- **Whitespace** is sometimes ignored and sometimes meaningful.

**Whitespace** means spaces, tabs, and similar invisible characters.

This is why the title says "as grammar." Comments and blank lines are mostly ignored, but whitespace — especially **indentation** and **newlines** — is part of Python's syntax.

If you get whitespace wrong, Python can raise:

- `IndentationError` — indentation is missing or inconsistent where Python expects a block.
- `SyntaxError` — the token arrangement is not valid Python.
- `TabError` — tabs and spaces are mixed inconsistently.

An error here means Python refuses to run the code because it cannot understand the structure.

---

## 5. Why does Python work this way?

Python uses **indentation** instead of braces like `{ }`.

In some languages, a block might look like:

```text
if (3 > 2) {
    print("yes")
}
```

Python instead writes:

```python
if 3 > 2:
    print("yes")
```

The indentation is not decoration. It tells Python: *"this `print` belongs inside the `if` block."*

The tradeoff: Python forces the visual structure of the code to match the logical structure. That makes code readable. But it also means invisible characters matter, so beginners must learn to "see" whitespace.

---

## 6. Why this matters in real code

This is not academic. In real jobs you will:

- debug syntax errors caused by indentation,
- read comments that explain why code exists,
- use blank lines to group code so humans can review it.

So the practical rule for now is:

> Python ignores some text, but not all text. Comments and blank lines are mostly for humans. Indentation and newlines are part of the grammar.
