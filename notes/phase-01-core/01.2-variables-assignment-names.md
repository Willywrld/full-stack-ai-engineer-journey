# Part A — The Concept Ladder

## §1 — Assignment: Binding a Name to a Value

### 1. The problem this solves
You compute a number once, but need it in three places. Without names you either retype it — and one typo silently corrupts your output — or nest expressions until they're unreadable. Concretely: a lab tech hardcodes `3.28084` (meters→feet) in six spots. The boss says "our standard factor changed to 3.281." You now have six edits and one guaranteed miss. **A name gives you one place to change, one place to read, one place to check.**

### 2. Mental model
A variable is not a box holding a value — it's a **sticky note with a name on it**, stuck onto a value that lives in memory. Assignment peels the note off whatever it was on and sticks it onto the new value.

### 3. Full syntax

```python
name = expression
```

- `name` — a legal identifier (§2 defines "legal").
- `expression` — anything that produces a value: `2.5`, `meters * factor`, `"kg"`.
- `=` here is the **assignment operator**, not mathematical equality. It means "evaluate the right side, then bind the left-side name to the result."
- `=` is a **statement**, not an operator — it produces no value of its own.

### 4. Behavior step-by-step
For `feet = meters * factor`, Python:

1. Evaluates the **entire right-hand side first**: looks up `meters`, looks up `factor`, multiplies them.
2. The result is a value object in memory (say, the float `8.2021`).
3. Binds the name `feet` — writes "feet" on a sticky note and sticks it to that object.
4. Done. If `feet` already existed, step 3 just re-sticks the note; the old value is untouched (§3).

Because `=` produces no value, `y = (x = 5)` is a `SyntaxError` — there's nothing for the outer `=` to grab. **The first "impossible in algebra, normal in code" moment.**

### 5. Line-by-line annotated code

```python
meters = 2.5                 # evaluate 2.5 -> a float object; stick the name `meters` on it
factor = 3.28084             # same: bind `factor` to the float 3.28084
feet = meters * factor       # RHS first: look up meters (2.5) and factor (3.28084),
                             #   multiply -> 8.2021; then bind `feet` to that result
print("feet:", feet)         # print shows values separated by a space -> "feet: 8.2021"
                             # it looks up `feet`, finds the float, displays it
```

- **Line 1** — RHS `2.5` is a float object. The name `meters` is bound to it. There is no declaration, no type annotation.
- **Line 2** — same, for `factor`.
- **Line 3** — **RHS evaluated first.** Lookup `meters` → 2.5; lookup `factor` → 3.28084; multiply → a *new* float object. `feet` is bound to that result. The old values of `meters` and `factor` are untouched — nothing was "consumed."
- **Line 4** — `print` takes two arguments: `"feet:"` and `feet`. It looks up `feet`, finds the float, displays `feet: 8.2021`.

### 6. When to use / when NOT to use
**Use** for any value used more than once; any value that carries *meaning* (a factor, a price, a threshold); any intermediate you'd want to inspect with `print` while debugging.

**Do not** name throwaway intermediates in a two-line calculation if the name adds noise. **Do not** use names like `x` or `data` for things that have a real identity — `conversion_factor` tells future-you the meaning; `x` doesn't.

### 7. Sibling comparison
- **`=` (assignment: bind a name) vs `==` (equality check: ask "are these equal?")** — one equals sign *stores*, two equals signs *ask*. Full treatment in §5.
- **`=` vs `:=` (walrus)** — an assignment that is also an expression. [Deferred to Phase 2: `:=` only earns its keep inside conditions/loops.]
- **Assignment vs. mathematical equality** — `x = x + 1` is impossible algebra and completely normal code — it means "compute `x+1`, then re-stick the name `x` on the result" (§3).

### 8. 🔓 Unlocks
- **R0 drills** — proving binding works.
- **R1 ticket** — "store the conversion factor once."
- **Every line of the anchor project.**

## §2 — Names: Legal Identifiers and Conventions

### 1. The problem this solves
Python must parse your code without ambiguity — so some names are **illegal** and must fail loudly. Simultaneously, *humans* must read your code — so some legal names are still **bad**. Two problems, two rule sets: **hard rules** (enforced by Python, `SyntaxError` if broken) and **conventions** (enforced by nobody, punished by every teammate and future-you).

### 2. Mental model
A name is a **label on a shipping box**: the courier (Python) rejects any label that breaks postal rules, and a good label tells the handler what's inside without opening it.

### 3. Full syntax

**Hard rules** — an identifier is legal if:
- It starts with a letter or underscore: `a–z A–Z _` (Unicode letters also work; ignore that for now — stick to ASCII).
- Every following character is a letter, digit, or underscore.
- It is not a **keyword** (reserved words Python owns: `if`, `class`, `for`, `def`, `return`, `import`, `True`, `False`, `None`, … — you'll meet each as we need it).

**One behavior, not a rule of spelling:** names are **case-sensitive** — `age`, `Age`, `AGE` are three unrelated names.

**Conventions** (PEP 8, official style guide — current, not legacy):
- `snake_case` for variables: `conversion_factor`.
- `ALL_CAPS` for constants: `MAX_ITEMS`. Python does **not** enforce this — it's a promise to the reader.
- Leading underscore (`_internal`) signals "not for outside use" — convention, becomes meaningful once modules exist. [Deferred to Phase 3.]
- Avoid single letters (`x`, `d`) except for very short-lived math.

### 4. Behavior step-by-step
Python's parser reads your file and turns text into **tokens** *before running anything*. A **keyword** is a token Python has claimed; `class = "Math"` fails at parse time — **the line never executes**. A **built-in** like `print` or `sum` is *not* a keyword: it's an ordinary name that already exists in Python's default namespace. You *may* rebind it — and then your name **shadows** the built-in for the rest of the file. Legal, and almost always a bug.

### 5. Line-by-line annotated code

**Legal names:**

```python
conversion_factor = 3.28084  # legal: starts with a letter, snake_case, descriptive
MAX_ITEMS = 100              # legal; ALL_CAPS = convention for "constant" (Python won't stop you changing it)
age = 30                     # legal
Age = 31                     # legal — and a DIFFERENT name: case-sensitive
print(age, Age)              # prints: 30 31
```

**Illegal names** — uncomment one at a time and run:

```python
# 2nd_place = "Bob"      # SyntaxError: name cannot start with a digit
# first-name = "Bob"     # SyntaxError: parsed as `first - name`; can't assign to a subtraction
# class = "Math"         # SyntaxError: `class` is a keyword, reserved by Python
# first name = "Bob"     # SyntaxError: spaces split this into three tokens
```

**Shadowing a built-in** — legal, dangerous:

```python
print = "I overwrote the built-in"   # LEGAL. Name `print` now points to a string.
# print("hello")                     # TypeError: 'str' object is not callable
                                     # (a string can't be "called" like a function — Phase 2 explains calls)
```

### 6. When to use / when NOT to use
- **Always obey hard rules** — you have no choice; they're enforced.
- **Follow conventions on every name**, including five-minute scratch files: habits are what survive deadlines.
- **NOT:** don't shadow built-ins (`print`, `sum`, `max`, `min`, `list`, `id`, `input`, `len`); don't use `l`, `O`, `I` as names (they read as 1/0 in many fonts); don't name something `data` or `temp` when a specific word exists.

### 7. Sibling comparison
Three tiers of "name you can't freely use":
- **Keyword** (`class`) — cannot be rebound. `SyntaxError`.
- **Built-in** (`print`) — *can* be rebound; doing so shadows it. Legal, dangerous.
- **Your own name** (`print_result`) — always safe, always preferred.

Also: `_private` (convention only) vs `__private` (name-mangling — real behavior) [Deferred to Phase 4].

### 8. 🔓 Unlocks
- Choosing safe names for the entire anchor project.
- R1 tickets.
- **R4 hardening habit** of never breaking built-ins.

## §3 — Rebinding and Augmented Assignment

### 1. The problem this solves
Real programs change over time: a running total across inventory items, a counter of processed rows, a measurement updated after calibration. You need to update a name's value repeatedly. Writing `total = total + item` every time is noisy — and worse, beginners believe this "changes the value," which leads to wrong predictions the moment two names are involved. **This section fixes both: the shorthand, and the mental model.**

### 2. Mental model
**Assignment never edits the old value.** It peels the sticky note off and sticks it on a newly computed value. `x += 5` is just a compact way to say "compute x+5, then re-stick the note `x`."

### 3. Full syntax

```python
name = expression-using-name          # explicit rebinding
name += expression                    # shorthand: name = name + expression
```

The augmented operators, all meaning "compute from the old value, then rebind": `+=`, `-=`, `*=`, `/=`, `//=` (floor divide), `%=` (remainder), `**=` (power). For the types you know now (numbers, strings), the shorthand is exactly equivalent to the long form — the difference only matters for mutable types, which you haven't met. [Deferred to Phase 3: why `+=` on a *list* can mutate it in place while `x = x + y` never does.]

### 4. Behavior step-by-step
For `total = total + 5` when `total` is `0`:

1. Evaluate RHS: look up `total` → `0`; add `5` → a **new** int object `5`.
2. Rebind: peel the note `total` off `0`, stick it on `5`.
3. The object `0` is unchanged; it's simply unreferenced, and Python frees it later.

`total += 5` performs exactly the same three steps. **Crucially — nothing in memory was edited; a name moved.**

### 5. Line-by-line annotated code

```python
total = 0
total = total + 5    # RHS: 0 + 5 -> new int 5; rebind total -> 5
total += 10          # identical to total = total + 10 -> 15
print(total)         # prints: 15

count = 1
count *= 3           # count = 1 * 3 -> 3
count -= 1           # count = 3 - 1 -> 2
print(count)         # prints: 2

a = 10
b = a                # b sticks to the SAME object a points at — assignment never copies
a = a + 5            # a rebounds to a NEW int 15; b still points at 10
print(a, b)          # prints: 15 10
```

The last block is the key prediction exercise: `b` followed the **old value**, not the *name* `a`. For numbers this is always safe. For objects you can change in place (lists, dicts), `b = a` means both names see changes — [Deferred to Phase 3: mutability and aliasing. You'll revisit this exact example with a list.]

### 6. When to use / when NOT to use
- **Use** for counters, running totals, state that legitimately evolves.
- **NOT:** **don't mutate a value you still need.** If the converter must print both the original and converted value, `meters *= 3.28084` destroys your input — use a new name: `feet = meters * 3.28084`. **The single most common real-world bug this section prevents.**
- **NOT:** `x = x` is a no-op; if you wrote it, you meant something else. And don't chain `+=` inside expressions — it's a statement; it has no value.

### 7. Sibling comparison
- **`x = x + 1` vs `x += 1`** — identical for numbers; difference is invisible until mutable types arrive (Phase 3).
- **`x += 1` (statement, rebinds a name) vs `x + 1` (expression, produces a value and throws it away if unassigned)** — `x + 1` alone on a line changes nothing; classic beginner bug.
- **Rebinding (moving the note) vs mutating (editing the value)** — same word "change" to humans, two different machine events. [Deferred to Phase 3: mutation.]

- **R1 "running total" ticket.**
- **Anchor milestone "accumulate converted readings."**
- **R4 break-it experiment "convert the same reading twice."**

## §4 — Multiple Assignment and Unpacking

### 1. The problem this solves
Two values travel together in the real world: a measurement *and* its unit, a width *and* a height, a record's item name *and* its quantity. Handling them on separate lines invites drift — update one, forget the other. Worse, the classic beginner bug: swapping two values with `a = b` then `b = a`, which silently destroys one of them. **Multiple assignment binds related values in one statement, and it's the only clean way to swap without a temporary name.**

### 2. Mental model
The right side is computed **completely first**, becoming a bundle of values; then sticky notes on the left are applied to that bundle left-to-right, all at once.

### 3. Full syntax

```python
a, b = 1, 2          # two names, two values
a, b = b, a          # swap — the idiom
width = height = 0   # chained assignment: one value, two names
```

- The right side `1, 2` is a **tuple** — a bundle of values without brackets. You'll meet tuples properly in Phase 3; for now, read `1, 2` as "the pair (1, 2)."
- Left side: names separated by commas. The count must match the bundle.
- No parentheses needed, though `a, b = (1, 2)` is the same thing.

### 4. Behavior step-by-step
For `a, b = b, a` when `a=10`, `b=20`:

1. Evaluate the whole right side: look up `b` → `20`, look up `a` → `10`, build the bundle `(20, 10)`.
2. *Now* apply the left side: rebind `a` → `20`, then `b` → `10`.
3. Note step 1 finished before step 2 started — **that's why the swap works, and why it needs no temporary variable.**

Chained assignment `width = height = 0`: evaluates `0` once, then binds `height` to it, then `width` to it. Both names point at the same `0` object. Harmless for numbers. [Deferred to Phase 3: with a list, chained assignment means two names share one object — a real bug source.]

**Error behavior — two failure modes:**

- Too few/many names for the bundle → `ValueError: not enough values to unpack (expected 2, got 3)`. **`ValueError`** means "right type of thing, wrong content."
- One indivisible value on the right → `a, b = 5` → `TypeError: cannot unpack non-iterable int object`. A single number cannot be split into two names; **`TypeError`** means "wrong kind of thing."

### 5. Line-by-line annotated code

```python
reading, unit = 12.5, "cm"       # RHS bundle (12.5, "cm") built first; then
                                 #   reading -> 12.5, unit -> "cm"
print(reading, unit)             # prints: 12.5 cm

reading, unit = reading * 2, unit  # rebind both from the OLD reading: bundle (25.0, "cm")
print(reading, unit)             # prints: 25.0 cm

left, right = 10, 20
left, right = right, left        # RHS bundle (20, 10) built first, then rebound
print(left, right)               # prints: 20 10

width = height = 0               # one int 0; both names stuck to it
print(width, height)             # prints: 0 0
```

### 6. When to use / when NOT to use
- **Use** for values that are meaningless apart (value + unit, x + y); swaps; initialising a couple of related counters.
- **NOT:** don't bundle unrelated values just to save a line — `factor, greeting = 3.28, "hi"` is worse than two lines. Don't unpack into more names than you'll use. Don't reach for it with lists/records of unknown length yet — that machinery is Phase 3.

### 7. Sibling comparison
- **`a, b = b, a`** (swap, one statement) vs the buggy **`a = b` then `b = a`** (both names end up on the same value — one value lost) vs the safe-but-noisy **`temp = a; a = b; b = temp`**. Know all three; prefer the first.
- **`width = height = 0`** (one value, two notes) vs **`width, height = 0, 0`** (two values, two notes). Identical result for numbers; different for mutable objects (Phase 3).
- **`a, b = 1, 2`** (unpacking a bundle) vs **`a = 1` / `b = 2`** (two assignments). Same outcome, different readability — choose based on whether the two values belong together.

## §5 — Assignment vs. Equality: `=` and `==`

### 1. The problem this solves
Two different questions get confused because their symbols look alike. "Store this" is not "ask whether these are equal." You need the second constantly: did the conversion land on the target? Is this label the expected one? Without a distinct operator, you can't ask questions in code — and the single most common beginner `SyntaxError` disappears once you can *see* the difference.

### 2. Mental model
`=` is a **verb** — *put it there*. `==` is a **question** — *is it equal?* — and questions produce answers (`True` / `False`), never store anything.

### 3. Full syntax

```python
name = value          # statement: binds a name. Produces nothing.
left == right         # expression: evaluates both sides, produces True or False
```

`==` is a **comparison operator**. It is an expression — it *has* a value — so it can be printed, stored, or used as an answer. `=` is a statement and has no value at all, **which is why it can never be nested inside another expression.**

### 4. Behavior step-by-step
For `print(feet == target)`:

1. Evaluate left: look up `feet` → `8.2021`.
2. Evaluate right: look up `target` → `8.2021`.
3. Compare → `True`. Print `True`.

The comparison rules you need now:
- **Numbers compare numerically across int and float:** `1 == 1.0` → `True`.
- **Strings compare character by character, case-sensitive:** `"cm" == "CM"` → `False`.
- **Different types are simply unequal:** `"1" == 1` → `False` (no error, just not equal).

And the collision: writing `x = 5` where you meant a question. At top level that's a legal *assignment* — it does the wrong thing silently. Inside a condition (`if x = 5:`) it's a `SyntaxError: invalid syntax. Perhaps you meant '==' instead?` — **modern Python 3.10+ literally suggests the fix.** [Deferred to Phase 2: `if` statements, where this collision bites hardest.]

### 5. Line-by-line annotated code

```python
meters = 2.5
feet = meters * 3.28084          # 8.2021 (approximately)
target = 8.2

print(feet == target)            # False — 8.2021 is not 8.2
print(meters == 2.5)             # True
print(1 == 1.0)                  # True — numbers compare by numeric value
print("cm" == "CM")              # False — strings are case-sensitive
print("1" == 1)                  # False — different types are simply unequal

result = feet == feet            # a comparison PRODUCES a value; store it like any other
print(result)                    # True
```

### 6. When to use / when NOT to use
- **Use `==`** whenever you're asking a yes/no question about values.
- **Do NOT use `==` on floats for exact equality.** Floats are binary approximations: `print(0.1 + 0.2 == 0.3)` prints `False`, because `0.1 + 0.2` is `0.30000000000000004`. This bites real projects (billing, sensors, conversions). For now, the honest workaround is to compare *rounded or formatted output* as strings — but f-string syntax you haven't earned. The plain Phase-1 version: print the value, eyeball it, and **don't build logic on float `==` yet.** [Deferred to Phase 4: comparing floats with a tolerance via `math.isclose`.]
- **NOT:** don't use `==` to check "is this the same object" — that's `is`. [Deferred to Phase 2.]

### 7. Sibling comparison
- **`=` (bind a name, statement) vs `==` (ask equality, expression) vs `!=` (ask *in*equality)** — all three will be your daily tools; `!=` behaves exactly like `==` with the answer inverted.
- **`==` (equal values?) vs `is` (the very same object?)** — looks similar, different question entirely. [Deferred to Phase 2.]
- **`==` (equality) vs assignment inside augmented form (`+=`)** — both touch values, only one produces an answer.

## §6 — Dynamic Typing and Case Sensitivity: What a Name Does *Not* Remember

### 1. The problem this solves
Two silent-failure classes that cost real hours. First: a name's *type* can change, so the same line of code can work on Monday and crash on Tuesday because the value behind a name changed. Second: `age` and `Age` look identical in a skimmed diff but are unrelated names — a classic bug when a report pulls the wrong field. **You need to predict both behaviors before they cost you.**

### 2. Mental model
**The sticky note has no memory of what it was stuck to before.** Types live on the *values*, not the names — so a name is only ever as typed as the value it's currently on.

### 3. Full syntax
Nothing new to type. The rule is a *behavioral* one:

```python
name = any_value      # legal, always — the name is untyped
```

There is no declaration line, no `int x;`. Python decides a value's type when the value is created, and checks that an operation is valid **at the moment it runs** — not when the file was written.

### 4. Behavior step-by-step
For `x = 5` then later `x = "five"`:

1. `5` is created as an int; note `x` sticks to it.
2. `"five"` is created as a str; the note `x` is peeled off the int and stuck to the string. The int is unchanged and now unreferenced.
3. Any later `x + 1` fails with `TypeError: can only concatenate str (not "int") to str` — because the value under `x` is now a string, and `+` on a string means "join text," which can't take a number. **The same line that worked before now crashes: the code didn't change, the value did.**

Case sensitivity is the spelling half of the same lesson: `age` and `Age` are two independent notes, always.

### 5. Line-by-line annotated code

```python
total = 0                        # name stuck to int 0
total = total + 5                # -> int 5
total = "5 items"                # LEGAL: note peeled off the int, stuck on a str
print(total)                     # prints: 5 items
# print(total + 1)               # TypeError: can only concatenate str (not "int") to str
                                 #   — because `total` now points at a string

age = 30
Age = 31                         # a different name entirely
print(age, Age)                  # prints: 30 31
# print(AGE)                     # NameError: name 'AGE' is not defined
                                 #   — never assigned; Python has no such note
```

Notice `NameError` vs `TypeError`:

- **`NameError`** = "I've never seen this name" (spelling/ordering problem).
- **`TypeError`** = "I know the name, but this operation doesn't work on this kind of value" (type problem).

**Reading which one you got tells you which mistake you made — that alone saves most debugging sessions.**

### 6. When to use / when NOT to use
- **Use the freedom:** prototyping, one-off scripts, values whose type legitimately settles later.
- **NOT:** don't let one name carry two *meanings*. If `total` is a number, it stays a number; when you need a display string, use a new name (`total_label`). A name that changes type mid-script usually means you're conflating "the data" with "the data as displayed."
- **NOT:** don't rely on case to distinguish names (`data` / `Data`). It's legal and it's a trap for every reader, including you at 11pm.

### 7. Sibling comparison
- **Dynamic typing** (Python: types live on values, checked at run time) vs **static typing** (C/Java: the *name* is declared with a type and locked to it). Python trades compile-time safety for speed of writing; you buy the safety back with tests and naming discipline, later.
- **`NameError`** (unknown name) vs **`TypeError`** (known name, wrong value kind) vs **`ValueError`** (right kind, unusable content) vs **`SyntaxError`** (unparseable text — often an illegal name or a stray `=`). **Four errors, four different fixes.**
- **Name rebinding** (moves the note) vs **value mutation** (edits the object). Still deferred to Phase 3 — but say it out loud now, because **it's the next thing that will surprise you.**

### 8. 🔓 Unlocks
- **Safe naming for the anchor.**
- **R4 hardening tickets** ("the client's file has a quantity field that's sometimes text").
- **The `=`/`==`/`NameError`/`TypeError` fluency you'll reuse in every atom from here.**

## Common Mistakes (8)

**M1 — `=` where you meant `==`.**
At top level it silently assigns; inside a condition it's a `SyntaxError` with a helpful hint. **Fix:** read the line aloud — "store" or "ask?"

**M2 — Illegal names.**
Starting with a digit (`2nd_place`), containing spaces or hyphens (`first name`, `first-name`), or using a keyword (`class`, `for`, `True`). All `SyntaxError` — **the file never runs.** **Fix:** letter/underscore start, only letters/digits/underscores, no keywords.

**M3 — `NameError` from typo or use-before-assignment.**
`print(totl)` or using `total` before the line that binds it. **Fix:** assignments execute top-to-bottom; a name exists only *after* its first binding line runs.

**M4 — Shadowing a built-in.**
`sum = 0`, `print = "hi"`, `list = []`. Legal, then a confusing failure later. **Fix:** name things `total_sum`, `print_result` — never overwrite a built-in.

**M5 — `x + 1` on its own line.**
Produces a value and throws it away; `x` is unchanged. **Fix:** if you meant to update, it's `x = x + 1` or `x += 1`.

**M6 — Using `+=` when you still need the original.**
`meters *= 3.28084` destroys the input; if the deliverable must show both, use `feet = meters * 3.28084`. **Fix:** augment only state that legitimately evolves.

**M7 — Case slips.**
`age`/`Age`, `total`/`Total`. **Fix:** pick a convention, never distinguish names by case.

**M8 — Believing `b = a` copies.**
It makes `b` point at the same value. For numbers it looks like a copy forever (safe); for lists it will not be. [Deferred to Phase 3: aliasing and mutation.] **Fix:** say "b now points at the same value," not "b is a copy of a."

## Performance & Complexity

- **Assignment is O(1)** — effectively instant. Binding a name is a dictionary-style insert into Python's current namespace; the cost does not grow with program size or with how many names exist.
- **Rebinding allocates, it doesn't edit.** `total = total + 5` builds a *new* int object and moves the note. For small numbers and short strings the cost is trivial; the important consequence is semantic (the old value is untouched and safe to still reference), not performance.
- **You never free memory.** Values with no names left pointing at them are reclaimed automatically (garbage collection). There is no `free()` in your future — so don't contort code to "save" names.
- **Names are free; clarity is the only budget.** Extra intermediate names cost nanoseconds and save hours. The one genuine cost to watch is *bad* naming, which has no complexity notation and a very high constant factor.

### Line-by-line reasoning

- **L8–L12 — the CONFIG block.** Five plain assignments, one value each. They are first because Python executes top to bottom and every later line needs them to already exist. `"Torque wrench T-40"` is a string in double quotes — the quotes are *not* part of the value; they are what tells Python "this is text, don't try to arithmetic it." `25.0` and `1.8` are floats (a decimal point makes it a float); `3` and `5` are ints. That int/float difference is why `Qty: 3` prints without a decimal point but `Length: 25.0` keeps its `.0` — Python prints a value in a form that shows its type.
- **Why these five are the only editable block.** The stakeholder's rule is "edit the top, run the file." Putting them above everything else makes the editable region a single visually obvious block — a human-factors decision, not a language one.
- **L15–L16 — the constants.** `ALL_CAPS` names the convention: "this is a lab constant, changing it changes every label." `0.393701` and `2.20462` each appear exactly once in the whole file. That is pass condition 4, and it's the direct fix for Priya's audit failure — one number to correct when SOP revisions the factor.
- **L19 — `length_in = length_cm * CM_TO_IN`.** Right side first: look up `length_cm` → `25.0`, look up `CM_TO_IN` → `0.393701`, multiply → `9.842525`. Then bind `length_in` to that new float. Note what is on the **left:** a *new* name. `length_cm` is untouched, so L28 can still print the metric value the receiving sheet is written in.
- **L20 — `mass_lb = mass_kg * KG_TO_LB`.** Same shape, same reasoning. That these two lines are the same *pattern* on purpose: derived values look identical, which is why they're trustworthy and reviewable.
- **L21 — `units_to_reorder = reorder_point - quantity`.** Subtraction, not conversion. Evaluates to `2`, an int (int − int = int), which is why it prints `2` and not `2.0`. If `quantity` were `5`, this prints `0`; if `7`, `-2`. **Both correct — the sign *is* the information** ("we are two over the reorder point").
- **L24 — the header.** A single string of exactly 18 `=`. It's a string because it's text; if you wrote `print(==================)` Python would try to parse `=` and fail with `SyntaxError`. Count the characters — 18, per spec, because the label sheet Priya prints on has an 18-character field.
- **L25 — `print("BENCH LABEL")`.** A literal string, no name involved. **Fixed text belongs in the print call, not in a variable** — a name here would be a name Priya could accidentally edit.
- **L26 — `print("Item:", item_name)`.** Two values, comma-separated. `print` converts each to text and joins them with a single space → `Item: Torque wrench T-40`. The space after the colon is *inside* the string, and the space after `:` before the name is supplied by the comma. **Two sources of one space — that's the pattern you must respect everywhere in this label.**
- **L27 — `print("Qty:", quantity)`.** Same pattern. The int `3` displays as `3`.
- **L28 — `print("Length:", length_cm, "cm /", length_in, "in")`.** Five values: `"Length:"`, `25.0`, `"cm /"`, `9.842525`, `"in"`. Comma-joined with single spaces gives `Length: 25.0 cm / 9.842525 in`. The `/` sits inside the `"cm /"` string because it's punctuation belonging to neither number. **This line is why originals are never rebound** — it reads `length_cm` *and* `length_in`, which is only possible because both names exist simultaneously.
- **L29 — same five-value pattern for mass.** Deliberately identical structure to L28: a reviewer checking the label format only has to learn one line shape.
- **L30 — `print("Units to reorder:", units_to_reorder)`.** The only line whose value can be negative, and the line most likely to alarm a beginner reading their own output. **It shouldn't — see the milestone-4 explanation.**
- **L31 — the footer.** Duplicated literal string rather than a name like `RULE = "=================="`. **Justification:** this atom's teaching point is *when* to make a name. A string that appears twice, never changes, and is read as fixed furniture is fine inline. Making it a constant is also defensible — if you did, say so in `reflection.md` and give the reason. [Deferred to Phase 4: the judgment rule for "constant vs. inline literal" in production code.]

### C.3.2 — Micro-scale client (exponent literals and visible float noise)

```text
STAKEHOLDER : Micro-fluidics lab — reports in µg and µL.
FAILURE     : Miscounting zeros at 1e-6 scale; noise surfaces in
              last digits.
```

**Task:** Produce `labeler_micro.py` handling gram/µg and mL/µL.

**Solution:**
```python
# labeler_micro.py — client: micro-fluidics lab, report in ug / uL

replicates = 3
mass_g = 0.0005
volume_ml = 0.0012
reorder_point = 5

# ---------- PER-LAB constants (two spellings of "one million") ----------
G_TO_UG = 1_000_000      # int literal; underscores are invisible to Python
ML_TO_UL = 1e6           # float literal: 1e6 means 1 x 10**6

# ---------- DERIVED ----------
mass_ug = mass_g * G_TO_UG
volume_ul = volume_ml * ML_TO_UL
units_to_reorder = reorder_point - replicates

# ---------- Report ----------
print("==================")
print("MICRO REPORT")
print("Sample:", sample_name)
print("Replicates:", replicates)
print("Mass:", mass_g, "g /", mass_ug, "ug")
print("Volume:", volume_ml, "ml /", volume_ul, "ul")
```

**Why correct:**
- `1_000_000` and `1e6` are the **same number, different types**: an int and a float. `0.0005 * 1_000_000` and `0.0005 * 1e6` take different arithmetic routes and can print different digits. Both are legally correct code; the type difference is real.
- Underscore separators in numeric literals are for *humans only* — Python discards them. Use them; they prevent miscounting zeros, which at `1e-6` scales is the actual failure mode.
- **The noise is the lesson, not a bug.** At 0.0005 g, the float's representation error is a larger *relative* share, so it surfaces in the last digits. [Deferred to Phase 2: `f"{mass_ug:.1f}"` to pin display digits. Deferred to Phase 4: `decimal.Decimal` for exact decimal arithmetic.]
- Unit labels `ug`/`ul` are inside the print strings, not in the names — names can't start with a digit but `mass_ug` is fine. **Keep units as suffixes** consistent with the anchor (`length_cm`).

**Real-world mirror:** Analytical labs live or die on significant figures and unit labels. Names carrying units are the cheapest defence that exists.

### C.3.3 — Invoicing client (integer cents, no floats at all)


**Task:** Produce `invoice_line.py` handling all amounts as **whole cents (ints)**.

**Solution:**

```python
quantity = 3
```

### C.3.4 — Sensor batch client (running total and a mean)

```text
STAKEHOLDER : Environmental bench — takes three readings per sensor
              and reports the mean.
FAILURE     : Dividing each reading by count before summing adds
              rounding errors; accumulator without an initial value
              → NameError.
```

**Task:** Produce `bench_batch.py` using an accumulator.

**Solution:**
```python
# bench_batch.py — client: environmental sensor bench

# ---------- PER-RUN ----------
sensor_name = "TH-9"
reading_1 = 21.5
reading_2 = 21.7
reading_3 = 21.4
reading_count = 3          # named, not retyped in the division

# ---------- DERIVED ----------
reading_total = 0.0        # accumulator starts as a float, so it stays a float
reading_total += reading_1
reading_total += reading_2
reading_total += reading_3

reading_mean = reading_total / reading_count

# ---------- Report ----------
print("==================")
print("SENSOR BATCH")
print("Sensor:", sensor_name)
print("Readings:", reading_1, reading_2, reading_3)
print("Count:", reading_count)
print("Total:", reading_total)
print("Mean:", reading_mean)
print("==================")
```

Expected: `Total: 64.6` (or `64.60000000000001`), `Mean: 21.533333333333335` (or `21.53333333333333`).

**Why correct:**
- `reading_total = 0.0` — the accumulator must exist **before** the first `+=`; otherwise `NameError`. Starting at `0.0` rather than `0` means the accumulator is a float from line one, so no int-to-float type switch mid-accumulation.
- Each `+=` reads the accumulator, computes, and rebinds — three rebinds, **no mutation of any reading.** The originals (`reading_1`…) are untouched and all three still print on the `Readings:` line. That is the anchor's "never destroy the input" rule enforced by having three separate names instead of one reused one.
- `reading_count` is a config name, not a literal `3` in the division. If the bench moves to five readings, the count changes once and the mean stays correct — the same one-place-to-edit logic as the conversion factors.
- `/` **always** produces a float, even when it divides evenly: `64.6 / 3` is a long decimal, and `6.0 / 3` would print `2.0`. **This is why the mean looks noisy while the total looks clean.**

**Real-world mirror:** Accumulate-then-divide is the shape of every averaging report ever written. **The failure it prevents:** dividing each reading by the count and summing, which adds three rounding errors instead of one.

```python
# Rule: nothing below the LABEL OUTPUT header may compute anything.
# Reason: a TypeError in the math then fires before a single label character is emitted.
length_in = length_cm * CM_TO_IN
mass_lb = mass_kg * KG_TO_LB
units_to_reorder = reorder_point - quantity
```

**Why correct:**
- The error text names the **types and the operator**: `int` and `str` with `-`. That tells you `reorder_point` is an int and `quantity` is a string — i.e., the *quotes* in the config are the bug, not the subtraction.
- Ordering is the entire fix. **Computation above output converts "half a label plus a traceback" into "a traceback and nothing to unstick from the instrument."**
- **What I cannot do at Phase 1:** route the traceback to a separate stream, or suppress stdout, or make the script exit with a specific code. [Deferred to Phase 4: `sys.stderr`, exit codes, and logging in Phase 5.] What I *can* do is make the blast radius zero.

**Real-world mirror:** A tech who gets a half label often assumes the printer faulted and reprints — with the same bad config.

### C.4.2 — One name per line, so the error names the culprit

```text
STAKEHOLDER : Priya — a config line is deleted accidentally.
FAILURE     : Combined derivations report only one missing name at a
              time; each run costs a cycle.
```

**Task:** Show that a combined derivation reports only *one* missing name, then restructure so the error points at the missing input directly.

**Solution — the failure, then the fix.** With `reorder_point` commented out:

```python
# ----- BAD: three dependencies on one line -----
print("Totals:", length_cm * CM_TO_IN, mass_kg * KG_TO_LB, reorder_point - quantity)
# NameError: name 'reorder_point' is not defined
```

```python
# ----- GOOD: one derivation per line, each named -----
length_in = length_cm * CM_TO_IN
mass_lb = mass_kg * KG_TO_LB
units_to_reorder = reorder_point - quantity
# NameError: name 'reorder_point' is not defined   <-- same message, but on ITS OWN line
```

And the config block gets the checklist contract:
```python
# ---------- PER-RUN: all FIVE lines required ----------
# [ ] item_name  [ ] quantity  [ ] length_cm  [ ] mass_kg  [ ] reorder_point
item_name = "Torque wrench T-40"
quantity = 3
length_cm = 25.0
mass_kg = 1.8
reorder_point = 5
```

**Why correct:**
- In the combined line, Python happens to name `reorder_point` — but that's **luck of evaluation order.** If two were missing you'd learn about one, fix it, re-run, learn about the next. Each run costs a cycle.
- One derivation per line means the traceback's line number **is** the diagnosis: the error lands on `units_to_reorder = reorder_point - quantity`, and that line has exactly two names, so the missing one is unambiguous.
- The commented checklist is a Phase-1 contract document. It does not execute; it exists so the person editing the file has a visible count. **Phase 1 has no validation — a written inventory is the honest substitute.** [Deferred to Phase 2: an `if` that checks presence and prints a warning.]

**Real-world mirror:** Config files are edited by people under time pressure, at the instrument, on a Friday. **Line-per-fact and a checklist cost nothing and survive that.**

### C.4.3 — Unit drift: millimetres typed into `_cm`

```text
STAKEHOLDER : Priya — a client typed a millimetre value into `_cm`.
FAILURE     : Unit mismatch is silent if the name doesn't carry the
              unit; the readout says "mm" in the sheet, "cm" in the
              label.
```

**Task:** Make the mismatch structurally impossible, and prove the rename is complete.

**Solution:**
```python
# ---------- PER-RUN ----------
item_name = "Arbor spacer A-12"
quantity = 4
length_mm = 25.0                # RENAMED: the name now states the real unit
mass_kg = 1.8
reorder_point = 6

# ---------- PER-LAB constants ----------
MM_TO_CM = 0.1
CM_TO_IN = 0.393701
KG_TO_LB = 2.20462

# ---------- DERIVED ----------
length_cm = length_mm * MM_TO_CM        # 2.5
length_in = length_cm * CM_TO_IN        # 0.9842525
mass_lb = mass_kg * KG_TO_LB
units_to_reorder = reorder_point - quantity

# ---------- Label ----------
print("==================")
print("BENCH LABEL")
print("Item:", item_name)
print("Qty:", quantity)
print("Length:", length_mm, "mm /", length_cm, "cm /", length_in, "in")
print("Mass:", mass_kg, "kg /", mass_lb, "lb")
print("Units to reorder:", units_to_reorder)
print("==================")
```

Expected: `Length: 25.0 mm / 2.5 cm / 0.9842525 in`, `Mass: 1.8 kg / 3.968316 lb`.

**Why correct:**
- The unit lives **in the name** (`length_mm`, `MM_TO_CM`), so the conversion chain is readable as a chain: mm → cm → in, one named factor per hop.
- **The rename ripple is the audit.** If you renamed the config but missed the derived line, you'd get `NameError: name 'length_cm' is not defined` — and that line is precisely where the stale unit assumption lives. **A missed rename cannot silently produce a wrong number; it produces a NameError.** That property is the reason to rename aggressively rather than add a comment saying "this is really mm."
- The label prints **all three units** because the sheet, the ERP, and the customer spec each want a different one. **Nothing is destroyed; each derived value has its own name.**
- `0.9842525` — the route mm→cm→in is two multiplications, so it does not necessarily match the anchor's `25.0 * 0.393701` digits. **Both are correct to the tolerance rule;** the route is documented by the names.

**Real-world mirror:** The Mars Climate Orbiter was lost to a unit mismatch between two teams' interfaces. **The Phase-1 defence is not a test suite — it's putting the unit in the identifier** so the wrong value looks wrong.

### C.4.4 — Put the SOP revision on the label

```text
STAKEHOLDER : Compliance — every printed label must state which
              conversion table produced it.
FAILURE     : A label without provenance is an unauditable claim.
```

**Task:** Make every printed label state which conversion table produced it.

**Solution:**
```python
# ---------- PER-LAB constants: SOP LB-114 rev 3 ----------
SOP_REV = "LB-114 rev 3"        # string constant: a constant need not be a number
CM_TO_IN = 0.393701
KG_TO_LB = 2.20462

# ---------- DERIVED ----------
length_in = length_cm * CM_TO_IN
mass_lb = mass_kg * KG_TO_LB
units_to_reorder = reorder_point - quantity

# ---------- Label output ----------
print("==================")
print("BENCH LABEL")
print("Item:", item_name)
print("Qty:", quantity)
print("Length:", length_cm, "cm /", length_in, "in")
print("Mass:", mass_kg, "kg /", mass_lb, "lb")
print("Units to reorder:", units_to_reorder)
print("SOP:", SOP_REV)
print("==================")
```

Expected final body line: `SOP: LB-114 rev 3`.

**Why correct:**
- `SOP_REV` is a **string** constant — constants are values that don't change per run, not values that are numbers. `ALL_CAPS` signals "don't edit at the top of a run," which is exactly the contract this string needs.
- The revision prints **inside the header/footer rules** as the last body line, so the label is self-documenting: **a filed label can be re-derived by hand from the correct table, years later.** A label without provenance is an unauditable claim.
- Placement matters: below the data, above the footer, so it reads as a stamp rather than a data field and cannot be confused with `Qty:`.
- **What this does not do:** it cannot *check* that the factor matches the revision string. A human can still bump the string and not the number. **Phase 1 has no mechanism for that.** [Deferred to Phase 3: one shared constants module so the string and the numbers travel together. Deferred to Phase 6: stamping a version from package metadata.]

**Real-world mirror:** Regulated industries require the revision of the reference table on the record. The cost of a `SOP:` line is one string; the cost of a missing one is an audit finding — **which is the story this whole anchor started from.**

### C.4.5 — The requested PASS/FAIL gate you must NOT ship

```text
STAKEHOLDER : Bench supervisor — wants a 'Matches nominal: True/False' flag.
FAILURE     : A wrong verdict on a label that a technician trusts is
              worse than no verdict at all.
```

**Task:** The client asks for `Matches nominal: True/False` on the label. You know from experiment X4 that `==` on floats is unreliable. **Produce the honest Phase-1 deliverable and document the limitation.**

**Solution — the demonstration, in a scratch file:**
```python
print(0.1 + 0.2 == 0.3)                 # False
print(25.0 * 0.393701 == 9.842525)      # record your machine's answer
```
Record the exact output. The first line is the canonical demonstration: **three floats the reader can see are "the same" compare unequal.**

**Solution — the shipped file (no flag):**
```python
# ---------- PER-LAB constants ----------
CM_TO_IN = 0.393701
KG_TO_LB = 2.20462
NOMINAL_LENGTH_CM = 25.0

# ---------- DERIVED ----------
length_in = length_cm * CM_TO_IN
mass_lb = mass_kg * KG_TO_LB
units_to_reorder = reorder_point - quantity

# ---------- Label output ----------
print("Length:", length_cm, "cm /", length_in, "in")
print("Nominal:", NOMINAL_LENGTH_CM, "cm")
# DEFERRED (Phase 4): a reliable "matches nominal" check needs a tolerance
# comparison, e.g. math.isclose(length_cm, NOMINAL_LENGTH_CM, abs_tol=0.01).
# Exact '==' on floats is not trustworthy — see experiments X4 / C.4.5.
# Until then the label shows measured and nominal side by side for human comparison.
```

**Why correct:**
- **Shipping a check you know is unreliable is worse than shipping no check.** A wrong `False` on a label that a technician trusts is a defect that damages trust in every other number on the page. A wrong `True` is worse: it passes a bad instrument.
- The label still delivers the *decision input*: measured and nominal, side by side, in the same units. **The technician's judgment is not removed — it's informed.**
- The deferred-work comment sits **at the point of absence**, where the next engineer will be standing when they ask "why isn't there a match flag?" **A deferral recorded in a chat message is a deferral lost.**
- **I did not invent an integer-scaling workaround.** Float floor-division comparisons can land on the wrong side of an exact boundary — a workaround that is *also* subtly wrong is not hardening. **Zero hand-waving means saying "I cannot do this correctly yet" and writing down why.** [Deferred to Phase 4: `math.isclose`.]

**Real-world mirror:** The most expensive bug class in measurement software is the check that returns the wrong verdict confidently. **Refusing to ship one is a senior-engineer decision, and this is the earliest atom where you can make it.**

## C.5 — Integration capstones (R4+)

*Everything in the atom, at working scale. Still Phase-1 legal — no `if`, no loops, no functions.*

### C.5.1 — Kit labeler: two entities in one file, prefix discipline

```text
STAKEHOLDER : Kit assembly FK-3 — parent and component both labelled
              with a total mass summary.
FAILURE     : Without prefixes, parent's mass gets rebound by the
              component block; under-declaring shipping weight.
```

**Task:** A kit ships with a parent item and a component. One file, one run, two label blocks and a summary.

**Solution:**
```python
# kit_label.py — client: kit assembly FK-3

# ---------- PER-RUN: parent ----------
kit_item_name = "Field kit FK-3"
kit_quantity = 1
kit_mass_kg = 6.4

# ---------- PER-RUN: component ----------
comp_item_name = "Spare probe SP-11"
comp_quantity = 2
comp_mass_kg = 0.35

# ---------- PER-LAB ----------
KG_TO_LB = 2.20462

# ---------- DERIVED ----------
kit_mass_lb = kit_mass_kg * KG_TO_LB
comp_mass_lb = comp_mass_kg * KG_TO_LB
comp_total_mass_kg = comp_mass_kg * comp_quantity
total_mass_kg = kit_mass_kg + comp_total_mass_kg
total_mass_lb = total_mass_kg * KG_TO_LB

# ---------- Label: parent ----------
print("==================")
print("BENCH LABEL")
print("Item:", kit_item_name)
print("Qty:", kit_quantity)
print("Mass:", kit_mass_kg, "kg /", kit_mass_lb, "lb")
print("==================")

# ---------- Label: component ----------
print("==================")
print("BENCH LABEL")
print("Item:", comp_item_name)
print("Qty:", comp_quantity)
print("Mass:", comp_mass_kg, "kg /", comp_mass_lb, "lb")
print("==================")

# ---------- Summary ----------
print("KIT TOTAL")
print("Total mass:", total_mass_kg, "kg /", total_mass_lb, "lb")
```

Expected: `6.4 kg / 14.109568 lb`; `0.35 kg / 0.771617 lb`; `Total mass: 7.1 kg / 15.652802 lb`.

**Why correct:**
- **Prefixes (`kit_`, `comp_`) are the whole point.** Without them, `mass_kg` would be rebound by the component block and the parent's mass would be lost — a variant of the anchor's cardinal sin, but self-inflicted. Prefixing makes collisions impossible by construction, and it scales: ten components would be `comp1_`, `comp2_`, …
- `total_mass_kg = kit_mass_kg + comp_total_mass_kg` — the component's *per-unit* mass is never added to the total; only the quantity-multiplied value is. **Getting this wrong under-declares shipment weight.**
- The label block is **duplicated verbatim** with different names. At Phase 1 there is no `def`, so duplication is the honest price of two labels. **Note in `reflection.md` that this duplication is exactly what a function removes** — that observation is the reason Phase 2 exists.
- `KG_TO_LB` is defined once and referenced four times; `2.20462` appears exactly once in the file.

**Real-world mirror:** Bills of materials, packing lists, and kit assembly all have this parent/child shape. **The prefix convention is what people do by hand before they learn nested data structures.**

### C.5.2 — Label + audit record: two artifacts, one run

```text
STAKEHOLDER : Lab SOP LB-114 rev 3 — the case label a technician
              reads, and the record an auditor reads.
FAILURE     : Mixing them produces a label with operator ID on it
              and a record with no formula trail.
```

**Task:** Produce (a) a case label a technician reads and (b) a record block an auditor reads, containing every input echoed back and every formula written out with its numbers.

**Solution:**
```python
# label_and_record.py — client: lab SOP LB-114 rev 3, audit-ready output

# ---------- PER-RUN ----------
item_name = "Torque wrench T-40"
quantity = 3
length_cm = 25.0
mass_kg = 1.8
reorder_point = 5
operator_id = "PT-07"

# ---------- PER-LAB ----------
SOP_REV = "LB-114 rev 3"
CM_TO_IN = 0.393701
KG_TO_LB = 2.20462

# ---------- DERIVED ----------
length_in = length_cm * CM_TO_IN
mass_lb = mass_kg * KG_TO_LB
units_to_reorder = reorder_point - quantity

# ---------- ARTIFACT 1: case label ----------
print("==================")
print("BENCH LABEL")
print("Item:", item_name)
print("Qty:", quantity)
print("Length:", length_cm, "cm /", length_in, "in")
print("Mass:", mass_kg, "kg /", mass_lb, "lb")
print("Units to reorder:", units_to_reorder)
print("SOP:", SOP_REV)
print("==================")

# ---------- ARTIFACT 2: audit record ----------
print("")
print("---- AUDIT RECORD ----")
print("SOP:", SOP_REV)
print("Operator:", operator_id)
print("INPUT item_name =", item_name)
print("INPUT quantity =", quantity)
print("INPUT length_cm =", length_cm)
print("INPUT mass_kg =", mass_kg)
print("INPUT reorder_point =", reorder_point)
print("CALC length_in = length_cm * CM_TO_IN =", length_cm, "*", CM_TO_IN, "=", length_in)
print("CALC mass_lb = mass_kg * KG_TO_LB =", mass_kg, "*", KG_TO_LB, "=", mass_lb)
print("CALC units_to_reorder = reorder_point - quantity =", reorder_point, "-", quantity, "=", units_to_reorder)
print("---- END RECORD ----")
```

Expected record lines include: `CALC length_in = length_cm * CM_TO_IN = 25.0 * 0.393701 = 9.842525`.

**Why correct:**
- **Two artifacts, deliberately separated.** The label is what gets stuck on metal; the record is what gets filed. Mixing them produces a label with an operator ID on it (noise on the case) and a record with no formula trail (useless in an audit).
- **Echo-back is the Phase-1 substitute for validation.** Every input is reprinted exactly as the program received it. If Priya typed `18` instead of `1.8`, the record shows it and the arithmetic is checkable by hand. **Phase 1 cannot *validate*; it can make the data transparent.** [Deferred to Phase 2: `if` checks that print warnings.]
- **Each `CALC` line prints the formula as literal text alongside the numbers.** An auditor can re-run the arithmetic on a calculator without reading the source. **That is the definition of an auditable record, and it costs one long `print`.**
- `print("")` emits a blank line — the only formatting tool Phase 1 has for visual separation between artifacts.
- `operator_id` is a **string** config value that appears only in the record, not the label. **Not every input belongs on every artifact; that judgment is the design work here.**

**Real-world mirror:** This is the difference between a tool that produces output and a tool that produces *evidence*. Regulated environments pay for the second one.

### C.5.3 — Two-route cross-check: independent verification as a feature

```text
STAKEHOLDER : QA lead — wants assurance the printed inch value is right.
FAILURE     : A single conversion path can have a wrong factor with
              no independent signal.
```

**Task:** Compute the inch value two independent ways — the SOP factor, and the exact definition (1 in = 2.54 cm) — print both, and report whether they agree exactly. **Interpret the result honestly.**

**Solution:**
```python
# crosscheck.py — client: QA, independent verification of the conversion

# ---------- PER-RUN ----------
item_name = "Torque wrench T-40"
length_cm = 25.0

# ---------- PER-LAB ----------
SOP_REV = "LB-114 rev 3"
CM_TO_IN = 0.393701        # SOP-rounded factor
CM_PER_IN = 2.54           # exact by international definition

# ---------- DERIVED: two independent routes ----------
route_a_in = length_cm * CM_TO_IN        # route A: multiply by the SOP factor
route_b_in = length_cm / CM_PER_IN       # route B: divide by exact cm-per-inch
routes_agree = route_a_in == route_b_in
difference_in = route_b_in - route_a_in

# ---------- Report ----------
print("==================")
print("CROSS-CHECK")
print("Item:", item_name)
print("Length:", length_cm, "cm")
print("Route A (SOP factor):", route_a_in, "in")
print("Route B (exact 2.54):", route_b_in, "in")
print("Difference (B - A):", difference_in, "in")
print("Routes agree exactly:", routes_agree)
print("SOP:", SOP_REV)
print("==================")
```

Expected: `Route A (SOP factor): 9.842525 in`, `Route B (exact 2.54): 9.84251968503937 in`, `Difference (B - A): -5.314960633010373e-06 in` (record your machine's exact digits), `Routes agree exactly: False`.

**Why correct:**
- **Two routes, one answer.** Route A applies the lab's rounded decimal factor; route B divides by the exact definition. If the code is right, the two land within the SOP's rounding tolerance of each other. **That's a real QA technique — independent computation — and it catches a wrong factor that no amount of code review would flag.**
- **`False` here is the correct, useful result.** `0.393701` is a rounded decimal of `1/2.54` (`0.3937007874…`), so on 25 cm the routes disagree by ~5.3 × 10⁻⁶ in. **That is the SOP's rounding error, made visible and quantified — not a bug.** Write the number in `reflection.md`.
- The `Difference (B - A)` line is what makes the report actionable. "They disagree" is noise; "they disagree by 5.3 micro-inches, which is 4 orders of magnitude below the instrument's resolution" is an engineering statement.
- **`routes_agree` uses `==` legitimately here — because the expected answer is `False`.** Using `==` to *detect* disagreement is safe; using it to *certify* agreement is not (C.4.5). **That distinction is the senior-level insight of this capstone.**
- `-5.314960633010373e-06` prints in exponent form because Python switches to scientific notation for very small floats. **That's not a formatting choice you made; it's how floats print.** [Deferred to Phase 2: f-string formatting to pin display.]

**Real-world mirror:** Cross-checking a derived value against a second, independent route is how metrology labs, finance reconciliation, and compiler test suites all work. **It is the cheapest correctness signal that exists before test frameworks arrive.**

# Part E — Interview-Style Problems

*Escalating. These are the questions a junior-hire technical screen actually asks about variables — plus the one that separates people who memorised the answer from people who understand the model.*

## E.1 — The Rebind Prediction (escalating from recall to reasoning)

**PROMPT.**
> "Read this code and tell me exactly what it prints, then explain why:
> ```python
> a = 10
> b = a
> a = a + 5
> a = "fifteen"
> print(a, b)
> ```
> Would any line raise an error?"

**STRONG-ANSWER WALKTHROUGH.**
> "It prints `fifteen 10`, and nothing raises an error.
>
> Line by line: `a = 10` binds `a` to the int 10. `b = a` evaluates the right side — looks up `a`, finds 10 — and binds `b` to *that same int object*. It does not copy anything; for an int it doesn't matter, because ints can't be changed. `a = a + 5` evaluates `10 + 5` → a new int 15, then rebinds `a` to 15. `b` is still on 10. Then `a = "fifteen"` is legal — Python names aren't typed, types live on values. `a` is peeled off the int and stuck on a string. So `print` shows `fifteen 10`.
>
> No error, because every line is a legal assignment. If I then added `print(a + 1)` it would raise `TypeError: can only concatenate str (not "int") to str` — that's the moment the type change becomes visible, and the error text tells me it's a type problem, not a naming problem.
>
> The one thing I'd flag: if `b = a` had been a *list* instead of an int, `b` would be an alias, and mutating the list through `a` would be visible through `b`. That's the part of this example that changes character with mutable types."

**WEAK ANSWERS.**
- ❌ "It errors on line 4 because `a` was a number." — Conflates names with types. Shows a box-with-a-type mental model.
- ❌ "It prints `fifteen 15` because `b` was assigned to `a`." — The classic copy/alias confusion *in reverse*: expects `b` to follow the *name* rather than the *value*. Direct evidence of the wrong mental model.
- ❌ "It prints `15 10` and line 5 errors because you can't mix types." — Right first half, invents an error. Can't distinguish "legal but later-fragile" from "illegal."
- ⚠️ "It prints `fifteen 10`. `b` copies the value." — Right output, wrong reason. Will fail the follow-up on lists.

**3-LEVEL RUBRIC.**
- **Level 1 — Correct output only.** States `fifteen 10`, no error. Can name that line 4 rebinds. *Pass, no credit for reasoning.*
- **Level 2 — Correct model, stated clearly.** Explains assignment as rebinding a name to a value; states explicitly that `b` points at the *old value*, not at the name `a`; knows the string reassignment is legal because names are untyped. Can name the error that *would* occur on `a + 1` and say it's a `TypeError`.
- **Level 3 — Model plus its boundary.** Everything in Level 2, **and** volunteers that the answer changes for mutable types: with a list, `b = a` makes an alias and mutation would show through both names; distinguishes *rebinding* (moves the name) from *mutating* (edits the object). Names the Phase in which that distinction is fully testable, rather than bluffing the detail.

**WHAT THE INTERVIEWER IS ACTUALLY MEASURING.** Whether "variable" means *a named reference to a value* or *a box holding a value*. The output is binary and easy; the model underneath is what determines whether this person will be surprised by every bug involving lists, function arguments, and default parameters for the rest of their career.

## E.2 — The Diagnostic (from reasoning to debugging)

**PROMPT.**
> "A colleague's script worked yesterday and fails today with no code changes:
> ```
> TypeError: can only concatenate str (not "int") to str
> ```
> Separately, a different file fails with:
> ```
> SyntaxError: invalid syntax. Perhaps you meant '==' instead of '='?
> ```
> For each: what class of mistake is it, what's the *fastest* path to the cause, and what would you change so it can't recur? Give me one sentence each on why these are different kinds of failure."

**STRONG-ANSWER WALKTHROUGH.**
> "**First error — `TypeError`.** The code didn't change, so a *value* changed. `TypeError` means Python found the names fine but the operation doesn't work on the kinds of values it found. `can only concatenate str` means the left operand of `+` is a string, so `+` was treated as "join text," and the right operand is an int — you can't join text to a number. The `+` is fine code; the data is wrong.
>
> Fastest path: the traceback's *last* line names the operation and both types — so I don't read upward hunting, I go to the line number the traceback gives. On that line I ask "which name could be holding a str here that held an int yesterday?" Usually it's config or file input that changed: a number typed with quotes, or a field that now arrives as text. Yesterday-vs-today means **input**, not logic.
>
> To stop recurrence: the bug is that one name carries two meanings — the *number* and the *number as typed*. Split them: `quantity` stays an int, and a display string gets its own name like `quantity_label`. Then the `+` can't silently change meaning. In a project that reads external data, I'd also add a check that the value is what I expect before doing arithmetic — but at Phase 1 my honest tool is one-name-one-meaning plus echoing inputs back so the bad value is visible.
>
> **Second error — `SyntaxError`, and it's a different *kind* of failure entirely.** The parser rejects the file before a single line executes. `invalid syntax. Perhaps you meant '==' instead of '='?` means I wrote `=` where a comparison belongs — the giveaway is that modern Python names the fix. Because it's pre-execution, nothing partially ran; there's no half-written output to worry about, and there's no data involved.
>
> Fastest path: the error already tells me the answer. I read the line and ask "store or ask?" — if I'm asking a question about values, it's `==`; if I'm putting a value into a name, it's `=`.
>
> To stop recurrence: the mistake is a *reading* failure, not a knowledge failure — everyone knows the difference under exam conditions. So the fix is naming: `=` belongs in a config/derived block near the top, `==` belongs in an expression that produces an answer and gets stored in a name whose verb says it's a check — `length_matches_nominal`, not `length_match_flag`. A name that reads like a question makes the operator's job obvious.
>
> **Why they're different.** A `SyntaxError` is a text problem: the file is unparseable, nothing ran, the error text names the fix. A `TypeError` is a data problem: the file is well-formed, it ran up to that point, and a *value* arrived with the wrong kind — which is why the investigation starts at the input, not the line. One is caught before execution; the other only at the moment the bad value meets an operation."

**WEAK ANSWERS.**
- ❌ "The first one means a variable has the wrong type — just cast it to int." — Doesn't ask *why* the value changed; a cast hides the upstream defect and will fail on any non-numeric string. No mention of input vs. logic.
- ❌ "The second is a typo, just add the second equals sign." — Fixes the symptom, never connects `=`/`==` to store/ask, offers no prevention. Will make the same mistake next week.
- ❌ Treats both as "the same kind of bug — Python complaining." — Cannot distinguish parse-time from run-time. This person will struggle to triage anything.
- ⚠️ "First is a TypeError, second is a SyntaxError. Fix the types and add an `=`." — Correct labels, zero investigative method, no prevention. Survives the label question, fails the debugging question.

**3-LEVEL RUBRIC.**
- **Level 1 — Correct classification.** Names `TypeError` as a run-time value/kind problem and `SyntaxError` as a parse-time text problem. Recognises `+` on str means concatenation.
- **Level 2 — Classification plus method.** Everything in Level 1, **plus** a concrete investigative path: read the traceback's type pair to identify which operand is the str; for the `SyntaxError`, use Python's own hint and ask "store or ask?" Explains that the unchanged-code-plus-changed-behaviour pattern points at *input*.
- **Level 3 — Method plus prevention plus the distinction stated cleanly.** Everything in Level 2, **plus** a structural fix for each: one-name-one-meaning / separate display name for the `TypeError`; question-shaped names and a config-vs-derived layout for the `=`/`==` collision. States explicitly that the `SyntaxError` prevented execution while the `TypeError` occurred mid-run — and therefore that one leaves no partial artifact while the other *can* (which is why the anchor computes everything before the first `print`).

**WHAT THE INTERVIEWER IS ACTUALLY MEASURING.** Whether the candidate has a *method* or a *vocabulary*. Most juniors can name four error types; far fewer can say what each one tells you to do next, and almost none volunteer that the parse/run split determines whether partial output exists.

## E.3 — The Refused Deliverable (the senior-engineer question)

**PROMPT.**
> "The client asks for a label line `Matches nominal: True` or `False`, comparing a measured float to a nominal target. You know exact `==` on floats is unreliable. At your current skill level you cannot implement a tolerance comparison. What do you ship, what do you tell the client, and how do you record the gap?"

**STRONG-ANSWER WALKTHROUGH.**
> "**First, the diagnosis, because the client's request is reasonable and I need to be specific about why it's unsafe.** Floating-point numbers are binary approximations of decimals. `0.1 + 0.2` is not exactly `0.3` — it's `0.30000000000000004` — so `0.1 + 0.2 == 0.3` prints `False`. Any measurement software doing exact `==` on floats will eventually print `False` for two values the technician can see are the same, or — worse, and less likely but far more damaging — `True` for something just inside a rounding boundary that shouldn't pass. A label that *confidently* gives a wrong verdict is worse than a label with no verdict, because the technician trusts it and stops looking.
>
> **What I ship.** The label shows **measured and nominal side by side, in the same units**, and nothing else:
> ```
> Length: 25.0 cm / 9.842525 in
> Nominal: 25.0 cm
> ```
> The decision input is complete and the human comparison is trivially easy — this is not a degraded deliverable, it's the same information with the verdict left where it belongs until I can compute it correctly. I do not ship a flag I know is unreliable, and I don't ship an integer-scaling workaround either — float floor-division comparisons can land on the wrong side of an exact boundary, so a workaround that's *also* subtly wrong isn't hardening, it's a second defect with better PR.
>
> **What I tell the client.** Plainly: 'The match check needs a tolerance band — a rule like "within 0.01 cm counts as matching" — and the tooling for that is in my next phase. Until then the label shows both numbers so your technician compares them directly. If you need the flag before then, I need you to tell me the tolerance the SOP specifies, and I'll implement it as soon as I have the right tool.' I give them the *decision* they need to make (what tolerance?) rather than a vague 'it's not ready.'
>
> **How I record the gap.** A comment at the exact point of absence — on the line after `Nominal:` where the flag would have gone — naming the limitation and the target phase:
> ```python
> # DEFERRED (Phase 4): reliable "matches nominal" needs a tolerance comparison,
> # e.g. math.isclose(length_cm, NOMINAL_LENGTH_CM, abs_tol=0.01).
> # Exact '==' on floats is not trustworthy — see experiments X4 / C.4.5.
> ```
> A deferral recorded in a chat message is a deferral lost; the next engineer will be standing at that exact line asking 'why isn't there a flag?' and the answer needs to be under their cursor. I'd also log it in the project's deferred-work list with the phase target, so it's tracked rather than buried.
>
> **One nuance I'd add.** Using `==` to *detect disagreement* between two independently computed values is safe — I expect `False`, and `False` is the useful answer. Using `==` to *certify agreement* is not safe. Same operator, opposite epistemic job. That distinction is what I'd want a reviewer to check in my work."

**WEAK ANSWERS.**
- ❌ "Just use `==` — it works for most values." — Ships the defect. Demonstrates no understanding of the failure mode.
- ❌ "Use `round(a, 2) == round(b, 2)`." — Plausible-sounding, still exact `==` on floats, and `round` on a float can return an int or a float with its own representation issue. Introduces a *new* unknown instead of removing one. (Also Phase-illegal here.)
- ❌ "Use `abs(a - b) < 0.01`." — Directionally right — this is essentially what `math.isclose` does — but it requires an `if` to produce a True/False to print, and it silently invents the tolerance the *client* must own. Honest answer acknowledges the approach and why the delivery is blocked, not just the arithmetic.
- ⚠️ "I'd ship the flag anyway and add a comment saying it's approximate." — A label that says `True` or `False` makes a promise. A comment in the source does not travel to the instrument case. This is the failure mode dressed as diligence.
- ⚠️ "I'd ship without the flag and tell them it's not possible." — Right deliverable, wrong communication. "Not possible" is false — it's *not yet correct at my skill level*, and the client owns the tolerance decision. Fails the stakeholder half of the question.

**3-LEVEL RUBRIC.**
- **Level 1 — Recognises the hazard.** States that exact `==` on floats can return `False` for values that "look" equal, and refuses to ship the flag. Cannot articulate what to ship instead.
- **Level 2 — Refuses and substitutes.** Level 1, **plus** a concrete alternative that preserves the decision input: measured and nominal printed side by side in matching units; explains that the human comparison is the correct Phase-1 substitute. Records the deferral *at the point of absence* with a target phase.
- **Level 3 — Refuses, substitutes, communicates, and distinguishes.** Level 2, **plus** a client-facing message that reframes the request into a decision the client must own (what tolerance does the SOP specify?), states explicitly *why* a confident wrong verdict is worse than no verdict, and distinguishes `==`-to-detect-disagreement (safe) from `==`-to-certify-agreement (unsafe). Optionally names the correct future tool and why a floor-division workaround is not an acceptable stand-in.

**WHAT THE INTERVIEWER IS ACTUALLY MEASURING.** Engineering judgment under incomplete tooling — which is the *normal* condition of professional work, not an edge case. The signal is whether the candidate can say "I cannot do this correctly yet, here is what I can do instead, here is what I need from you, and here is where I recorded it" without either faking the feature or hiding behind "not possible." That sentence *is* the job.

# Part F — Quick-fire Q&A

*Rapid recall. One paragraph each. If you can't produce the gist of any answer in under ten seconds, that's the section to re-read before you build.*

### F.1 — What is a variable in Python, in one sentence that would survive a code review?
A variable is a *name bound to a value* — a sticky note on an object in memory, not a container holding a copy. The name carries no type of its own; the type belongs to whatever value the name currently points at, and that can change on the next assignment line. Everything downstream follows from this: `b = a` makes `b` point at the same object rather than copying it, `a = "text"` after `a = 5` is legal, and rebinding a name never edits the value it used to point at.

### F.2 — Why doesn't `b = a` copy the value, and when does that difference actually bite?
Assignment evaluates the right side and binds the *left-side name* to whatever object that evaluation produced — it never duplicates the object. For numbers and strings this is invisible, because those values cannot be changed at all, so "shared" and "copied" behave identically forever. The difference becomes a real bug the moment the shared value is a mutable object: with a list, changing it through `a` is visible through `b`, and beginners who believe assignment copies will spend an afternoon on a bug with no typo in it. [Aliasing and mutation: Phase 3 — but say "points at," never "is a copy of," from today.]

### F.3 — `=` versus `==` — what's the actual difference, and why is one of them a `SyntaxError` trap?
`=` is a **statement** that binds a name and produces no value; `==` is an **expression** that compares two values and produces `True` or `False`, which you can print or store like any other value. Because `=` has no value, it can never be nested inside an expression — so `if x = 5:` fails at parse time with `SyntaxError: invalid syntax. Perhaps you meant '==' instead?`, and the file never runs at all. At top level, though, `x = 5` where you meant a comparison is perfectly legal and silently does the wrong thing, which is the more dangerous version of the same confusion.

### F.4 — What makes a name legal, and what's the difference between a rule and a convention?
Hard rules — enforced by the parser, `SyntaxError` if broken: start with a letter or underscore, continue with letters/digits/underscores only, and don't use a keyword (`if`, `class`, `True`, `for`, …). Conventions — enforced by nobody, punished by every reader: `snake_case` for variables, `ALL_CAPS` for constants, descriptive names over `x`/`tmp`, no shadowing built-ins like `print` or `sum`. The distinction matters because the second category is where real damage happens: `max = 12` is legal, runs fine, and then breaks an unrelated `max(a, b)` forty lines later with a `TypeError` that points nowhere near the cause.

### F.5 — What is dynamic typing, and what's the honest cost of it?
Types live on *values*, not on names: Python checks that an operation is valid at the moment it runs, not when the file was written, so a name can point at an int on Monday and a string on Tuesday. The benefit is speed of writing — no declarations, no ceremony. The cost is that a `TypeError` can appear in code that hasn't changed, because the *data* changed, which means your investigation starts at the input rather than at the line. You buy the safety back later with type hints and tests [Phase 4]; at Phase 1 you buy it with one-name-one-meaning and by never letting a name carry both a value and its display form.

### F.6 — Four errors, four fixes: `SyntaxError`, `NameError`, `TypeError`, `ValueError`.
`SyntaxError` is a *text* problem — the file can't be parsed, so nothing executed at all; fix the spelling, the illegal name, or the stray `=`. `NameError` is a *naming* problem — the file parsed and ran until a line referenced a name that had never been bound (typo, or used before its assignment line); fix the spelling or the ordering, and trust the name Python reports as the one it couldn't find. `TypeError` is a *kind* problem — the names were all found, but the operation doesn't work on these kinds of values (`"3" - 1`, calling a string); fix the value, not the code. `ValueError` is a *content* problem — right kind, unusable content (unpacking three values into two names); fix the data. One error text, one investigation direction.

### F.7 — What does `+=` do, and what's the one situation where using it is a defect?
`total += 5` is exactly `total = total + 5`: evaluate the old value plus five into a new object, then re-stick the name on the result — no object is edited. It's a defect whenever the original value is still needed, which in a labelling tool is *most of the time*: `length_cm *= 0.393701` destroys the metric reading that the label must still print, producing a line that says `1.8 kg / 1.8 lb` and looks plausible. Augment state that legitimately evolves — counters, accumulators — and derive everything else into a new name. [Phase 3 will add the second reason to be careful: on a list, `+=` can mutate in place while `x = x + y` never does.]
